# zxlog v0.7 升级说明

> 适用范围：Linux/ELF + C++17 + GN/Ninja；以当前仓库原有的镜像身份、字典、PathLease、FileWriter、Diagnostics 为稳定基座。v0.7 在独立分支验证，不直接覆盖 main。

## 与 v0.4 的兼容边界

- **源代码 API**：继续支持 `ZX_LOG(INFO, "...", ...)` 与 `ZX_LOG(logger, INFO, "...", ...)`，包括括号包裹的复杂 logger 表达式；`Logger::create()` 仍可用。新增 Options 字段会改变对象布局，所有调用方须重新编译。
- **日志协议**：新二进制日志为 `ZXLOG03\0`、wire-version 3；整数使用 ULEB128 / ZigZag，字符串长度使用 ULEB128，float/double 保持 IEEE754 小端。CRC32 记录头和 64 字节文件头不变。离线 C++/Python 解码器继续读取 `ZXLOG01\0` 和 `ZXLOG02\0`；历史固件日志须配它自己的字典。
- **身份验证**：最终 ELF 必须经过 `extract_dictionary.py` 身份固化与 `strip_metadata.py` 校验/剥离；使用错误字典或未固化镜像会拒绝初始化。
- **默认调度**：不设置 `Options::dispatcher` 仍是每 Logger 独立消费者线程。共享 Dispatcher 只是可选优化。
- **编译期级别**：`zxlog_active_level` 默认为 0（TRACE），数值 0..6 依次对应 TRACE/DEBUG/INFO/WARN/ERROR/CRITICAL/OFF。被关闭的日志点通过宏预处理彻底移除，参数不求值、元数据不生成。

## 1. 有界队列内存

```cpp
zxlog::Options opts;
opts.max_producers = 4;
opts.per_thread_slots = 64;
opts.max_record_bytes = 256;       // 包含 20 字节记录头；32..1024
opts.max_queue_bytes = 128 * 1024; // 生产者槽位和元数据预算
```

队列容量预算 = `max_producers * per_thread_slots * (max_record_bytes + sizeof(Slot))`，当预算不足时 `initialize()` 失败，且不打开日志文件。可以通过 `logger.stats().queue_payload_bytes` / `queue_memory_bytes` 查询预分配规模。预算不包括线程栈、文件 I/O 缓冲区、日志字典和容器自身分配开销；不等于进程 RSS 上限。超长日志整体丢弃，`record_too_large` 计数增加，绝不发布部分事件。

## 2. Sink 抽象

```cpp
#include "zxlog/zxlog.h"
#include "zxlog/sink.h"

zxlog::Options opts;
opts.extra_sinks.push_back(std::make_shared<zxlog::ConsoleSink>());
// Logger::create(opts, &error) 前按现有流程准备匹配的镜像身份、字典和输出路径
```

主文件输出通过 `FileSink` 复用原有 `FileWriter` 和 `PathLease`。新增自定义 `Sink` 可实现 `mode()`、`append()`、`flush()`、`close()`。TEXT 收到格式化的完整文本行；BINARY 收到带 CRC 的完整事件记录（不包含文件头）。自定义 Sink 的方法是 `noexcept`，禁止在回调内部同步调用相同 Logger 的 `flush/shutdown`；共享 Sink 的多线程同步由实现方负责。出现写入失败时会记录诊断错误，影响 `flush` 的成功状态。

## 3. 共享 Dispatcher

```cpp
#include "zxlog/dispatcher.h"
auto shared_dispatcher = std::make_shared<zxlog::Dispatcher>();
zxlog::Options motor_opts, navigation_opts;
motor_opts.dispatcher = shared_dispatcher;
navigation_opts.dispatcher = shared_dispatcher;
// 为两个 Logger 分别配置不冲突的文件路径，并采用现有 Logger::create() 初始化
```

共享调度采用单工作线程和轮询公平批次。关键生命周期约束：先停止业务线程，再关闭各 Logger，最后释放 Dispatcher。解绑先排空各 Logger，随后等待该 Entry 的正在执行回调结束；注册表互斥锁不跨文件 I/O。**共享线程仍然可能受到慢 Sink 的队头阻塞**，因此关键安全日志、长时间 fdatasync 或可能阻塞的 Sink 建议使用独立 Logger 工作线程。

## 4. 构建与验证

```bash
gn gen out/Binary --args='zxlog_mode="BINARY"'
ninja -C out/Binary check
gn gen out/Text --args='zxlog_mode="TEXT"'
ninja -C out/Text check
gn gen out/Runtime --args='zxlog_mode="RUNTIME"'
ninja -C out/Runtime check

# 编译期仅保留 ERROR、CRITICAL：
gn gen out/Filtered --args='zxlog_mode="BINARY" zxlog_active_level=4'
ninja -C out/Filtered zxlog_all
```

可选参数：`zxlog_cc`、`zxlog_cxx`、`zxlog_linker`、`zxlog_archiver`、`zxlog_extra_cflags` 和 `zxlog_extra_ldflags`，用于 GCC LTO、Clang Sanitizer 和交叉编译定制。

## 5. 发布前还需要评估

- 目标 ARM SoC 的 CPU/RSS/Flash、P50/P99 日志调用延迟及存储写放大。
- 文件系统掉电、磁盘空间耗尽、轮转失败以及慢 Sink 队头阻塞的故障注入。
- 多生产者高峰容量，按实测确定 `max_producers`、槽位数和丢弃策略。
- 跨固件升级必须归档每次部署对应的 `.zdict` 与 manifest，不能用新字典恢复旧日志。
